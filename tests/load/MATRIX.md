# Автономный прогон по числу устройств

Запускается с Node.js 20+ на компьютере генератора. Диалог Codex после запуска
можно закрыть. Компьютер должен оставаться включённым, без сна; сеть и SSH-туннель
(если используется) должны продолжать работать. Нагрузка идёт только на уже
подготовленный изолированный Appwrite-стенд из [runbook](../../docs/audit-runbook.md).
Скрипт не поднимает серверы, не создаёт данные и не переключает production.

Нужен приватный актуальный `fixture.json` от этого стенда: он содержит тестовые
сессии, выданные на 24 часа. Просроченные сессии нужно обновить перед замером;
не отключайте проверку авторизации. Файл и результаты храните вне Git-репозиториев.

Пример для терминала macOS/Linux из корня проекта (замените путь к fixture,
`RUN_ID`, транспорт и URL сборщика ресурсов на свои):

```sh
npm run load:matrix -- \
  --fixture /private/tmp/ifm-audit/fixture.json \
  --output /private/tmp/ifm-load-20261022-01 \
  --confirm-run RUN_ID \
  --devices 10,25,50,100,200 \
  --stage-seconds 600 --warmup-seconds 180 \
  --transport ssh-tunnel \
  --resource-status-url http://127.0.0.1:28088/audit-resources/PHASE/status.json \
  --software-version COMMIT \
  --allow-load --allow-writes --detach
```

`--detach` сохраняет PID и возвращает управление терминалу. Отключение самого
генератора, выход из пользовательского сеанса или остановка SSH-туннеля прервут
работу. На Mac можно дополнительно удерживать компьютер от сна командой
`caffeinate -i -w PID`, подставив выданный PID.
На Windows команда Node также поддерживается, но пути и переносы строк следует
заменить на синтаксис PowerShell.

Без `--detach` тот же сценарий работает в переднем плане. `--dry-run` вместо
`--detach` показывает план и фактическое распределение типов экранов, не посылая
сетевых запросов и не создавая каталог результатов. Для проверки плана
`--allow-load` не требуется. Неизвестные параметры, недостаточное число уникальных
сессий и повторное использование каталога отклоняются.

По умолчанию: 3 минуты разогрева и 5 ступеней по 10 минут — **53 минуты**
плановой нагрузки плюс контрольные запросы и до 17 секунд ожидания доставки
после каждой ступени. Можно задать, например, `--devices 10,50,100` и
`--stage-seconds 300`. Числа строго возрастают и ограничены числом уникальных
экранных сессий fixture (обычно 200). Новые сессии скрипт не выдумывает.

Устройство здесь означает экранную HTTP-сессию. Сотрудники и операторы создают
дополнительные запросы по прежнему сценарию; их число фиксируется в событиях.
Берётся префикс исходного fixture, поэтому реальная смесь server/modern/legacy
для каждой ступени записывается в `plan.json`; малая ступень может состоять
только из server TV. Это моделирование HTTP, а физические экраны и браузерный
рендеринг требуют отдельной проверки.

С `--allow-writes` сотрудники меняют тестовые остатки, цену, доступность и перерыв;
без этого флага выполняются чтения, а доставка изменений не проверяется.
Все ступени последовательно используют одну БД, без сброса между ними. Это новый
профиль `matrix`, он не заменяет прежний `full` с часовым soak и reload.
В `matrix` маршрутные SLO проверяются на всех ступенях кроме разогрева.

Сохраняются прежние защиты: проверка идентичности тестовой БД, запрет публичных
и production-адресов, таймауты, лимит одновременных запросов, остановка при >5%
ошибок или p95 >3 с в минутном окне с минимум 20 ответами. При переданном URL
сборщика ресурсов устаревшая телеметрия или аварийный сигнал останавливают нагрузку.
Сам Windows-сборщик запускается отдельно по runbook; генератор не собирает
ресурсы хоста. Без URL сборщика автоматического контроля CPU/RAM нет.

Наблюдение и остановка:

```sh
cat /private/tmp/ifm-load-20261022-01/runner.json
tail -f /private/tmp/ifm-load-20261022-01/console.log
# Остановить; дождаться итогового runner.json перед сбором файлов:
touch /private/tmp/ifm-load-20261022-01/STOP
```

В PowerShell для остановки: `New-Item C:\results\RUN\STOP -ItemType File`.
Остановка занимает текущую проверку/запрос (таймаут до 10 с), затем формируется
отчёт. SIGINT/SIGTERM также обрабатываются. Принудительное убийство процесса,
выключение компьютера или заполнение диска могут оставить только частичные журналы.

После обычного завершения или управляемой остановки собрать весь каталог:

- `runner.json` — `running/completed/failed/stopped`, PID, итог проверки, причина остановки;
- `plan.json` — ступени, продолжительность и фактическая смесь экранных клиентов;
- `stages.csv` — сводка по числу экранов: запросы, ошибки, p95, пропуски, RPS;
  незапущенные и прерванные ступени помечены отдельно;
- `console.log` — вывод фонового процесса;
- `workload/report.html`, `routes.csv`, `requests.csv` — автоматически созданные отчёты;
- `workload/manifest.json`, `summary.json`, `requests.jsonl`, `events.jsonl` — исходные доказательства.

`completed` означает завершение с пройденными проверками, `failed` — ошибку
исполнения/отчёта либо непройденную приёмку. Превышение аварийного порога даёт
`stopped`; следующие ступени не запускаются. Файл `runner.json` с `endedAt`
обозначает завершение обработки результатов.
RPS ступени включает время завершения запросов и ожидания доставки, как в
основном отчёте. Общий p95 ступени смешивает маршруты; маршрутные SLO смотрите
в `workload/summary.json` и `routes.csv`.

Ресурсные JSONL и API-логи с Windows нужно сохранить отдельно. После их получения
HTML можно пересобрать с ресурсными графиками:

```sh
node tests/load/report.mjs \
  --input /private/tmp/ifm-load-20261022-01/workload \
  --resources /external/windows-resources.jsonl
```

Если нужна сверка статистики, снимки `reconcile.mjs snapshot` должны охватывать
весь прогон и выполняться без других писателей (см. основной README).
Сами fixture, секреты и конфигурацию стенда в отчёт не копировать.
